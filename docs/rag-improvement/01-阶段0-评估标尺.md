# 阶段 0：先造一把不会骗人的尺子（检索评估入门）

> 面向入门：本文解释「评估标尺」是什么、有没有公认标准、怎么建、怎么用、用什么技术栈，并记录本项目实际落地结果与反思。
> 配套代码：`eval/retrieval_metrics.py`、`eval/run_eval.py`、`eval/calibrate_threshold.py`、`eval/golden_set*.jsonl`。
> 语料：`data/论语.pdf`（52 页）与本地需求文档转换出的 `data/rag_requirements.txt`（304 段，不纳入版本管理）。

---

## 1. 为什么先做评估，而不是先改检索

改造前，RAG 的链路是：

```text
query → Chroma 向量检索 k=3 → 拼 context → qwen 生成
```

想判断“改成 k=10 会不会更好”，只能凭感觉。问题是：

- 改 `chunk_size`、换 Embedding、加 BM25、加 rerank，每一个都会改变结果；
- 没有固定题库，就无法区分“真的变好”和“这次问的问题恰好简单”；
- 没有分桶，就不知道是“精确标识符”坏了，还是“语义型”坏了。

**评估标尺 = 固定的问题集（Golden Set）+ 固定的指标脚本 + 可归档的结果快照。**
它不面向用户，唯一作用是让后续每一次架构决策都有数字依据。

## 2. 有公认标准吗？分三层看

### 2.1 指标定义：有，直接照抄

信息检索（IR）领域从 TREC（NIST 1992 年起）就确立了评测范式，BEIR / MTEB 把它标准化。项目使用四个二元相关性指标：

| 指标 | 公式 | 回答的问题 |
| --- | --- | --- |
| Recall@K | `命中相关块数 / 全部相关块数` | 该找到的证据找全了吗 |
| HitRate@K | `Top-K 是否至少有一个相关块` | 有没有完全跑偏 |
| MRR@K | `1 / 第一个相关块的排名` | 第一条对的排得靠不靠前 |
| NDCG@K | `DCG@K / IDCG@K`，`DCG = Σ rel_i / log2(i+1)` | 整体排序质量如何 |

BEIR 用 nDCG@10 作为统一汇报指标，因为它兼容二元/分级相关性且对位置敏感。但入门阶段 **Recall@10 + MRR@5 足够**：召回漏掉的东西，后面的精排永远救不回来（v2 的原话）。

### 2.2 框架：RAGAS 是生成侧的事实惯例，不是“标准答案”

RAGAS 的 `Faithfulness`、`Context Recall` 等指标是 LLM-as-judge 算出来的，会随裁判模型版本漂移。v2 要求裁判与人工标注算 Cohen's κ，κ<0.6 视为不可用。**阶段 0 完全不碰生成侧**，只做确定性的检索指标；RAGAS 留给后续阶段。

### 2.3 数据集：只能自建，公开集不能代替

BEIR/MTEB 榜单用于**选 Embedding 模型**，不能回答“我的知识库上检索得好不好”。公开集最多用来验证你的评估脚本本身算得对。

> 结论：公式照抄 IR 标准；RAGAS 是生成侧惯例；**数据集必须用自己的语料自建**。

## 3. 一把好尺子的六个属性

### 3.1 标注目标是「块」，不是「文档」或「文本」

标整篇文档会让指标虚高；标文本难以精确匹配。正确做法是标 `chunk_id`。

但 Chroma 自动生成的 UUID 每次重建都会变，标注会全部作废。因此阶段 1 先实现了**确定性 ID**：

```text
version   = 文件内容 md5
chunk_id  = {doc_id}#{version[:8]}#c{seq:04d}
parent_id = {doc_id}#{version[:8]}#p{seq:04d}
```

同一文件 + 同一套分块参数 → 同一批 ID。这是标注可以跨天、跨机器复用的前提。

### 3.2 覆盖度按查询类型分层，并掺负样本

| 类型 | 考什么 | 本项目条数 |
| --- | --- | --- |
| identifier（精确标识符） | 词面匹配、专名、引文 | 19 |
| semantic（语义型） | 同义改写、概念解释 | 22 |
| multi_condition（多条件） | 同时命中多处 | 10 |
| multi_hop（多跳） | 需要 2 条以上证据 | 8 |
| unanswerable（不可回答） | **该拒答** | 12 |

负样本至少 10%。它的作用是让“返回一堆东西”不再自动等于高分，也是后续 Answerability 阈值校准的唯一依据。

### 3.3 可复现：离线、确定、零 LLM 调用

阶段 0 的指标脚本不调用任何生成模型；断网也能跑（除 embedding/rerank 外）。只要引入 LLM 打分，就无法判断“分块策略改动”带来的差异——噪声比信号大。

### 3.4 有随机基线

小语料上随机检索也可能得高分。每次报告都附：

```text
随机 Recall@10 ≈ 1 - C(N-R, 10) / C(N, 10)
```

本项目 N=239 个块，随机基线为 **0.0866**。如果系统只有 0.15，说明几乎没有超出随机水平。

### 3.5 语料规模要够

改造前只有 3 个块（`测试文本.txt` 全文 4 行、`测试pdf2.pdf` 只有 2 个字符），任何指标都会接近 1.0 或没有区分度。本次加入 `论语.pdf`（26,093 字，142 个子块）与需求文档（16,663 字，95 个子块），总块数 239，才具备评测意义。

### 3.6 防过拟合与防漂移

- **版本化**：记录 `index_version`、Embedding 模型、分块参数；
- **holdout**：本次尚未拆分 train/holdout，是已知缺口；
- **回流**：badcase 每月补入，不要建完就放着。

## 4. 怎么建：本项目的实际流程

### Step 1｜语料准备

- `data/论语.pdf`：`PyPDFLoader` 读取 52 页，正文约 26K 字；
- `data/rag_requirements.txt`：`eval/prepare_local_corpus.py` 解包 docx 生成，保留 `##` / `###` 标题层级；与 `.docx` 一样不纳入版本管理。

### Step 2｜结构化分块与稳定 ID

`rag/chunking.py` 的做法：

1. 识别 Markdown 标题、`卷X　篇名`、`第X章`；
2. 《论语》的「子曰/有子曰/某某问」作为独立块边界；
3. 父块约 900 字（标题 + 连续段落），子块 240 字 / overlap 40；
4. 每个子块写入 `doc_id/version/chunk_id/parent_id/page/char_start/char_end/title_path/content_hash/scope_tags/index_version`。

结果：`论语` 52 父块 / 142 子块；`rag_requirements` 42 父块 / 95 子块；总计 **96 父块 / 239 子块**。

### Step 3｜写 Golden Set

`eval/golden_set.jsonl`（论语，50 条）+ `eval/golden_set.local.jsonl`（需求文档，21 条）。

每条记录示例：

```json
{
  "id": "ly-001",
  "query": "孔子认为学习之后应该怎么做？",
  "query_type": "semantic",
  "answerable": true,
  "relevant_snippets": ["学而时习之，不亦说乎"],
  "ground_truth": "学习之后要经常温习、实践。",
  "notes": "学而第一",
  "corpus": "论语"
}
```

**为什么存片段而不是直接存 chunk_id？** 片段在评测时归一化（去空白/标点）后映射到块；这样切分参数变化时标注仍可复用。映射逻辑在 `eval/retrieval_metrics.py:resolve_snippets()`。

### Step 4｜写指标脚本

`eval/run_eval.py` 支持三种模式共用同一批 Golden Set：

```text
dense  = 纯向量（旧实现基线）
hybrid = Dense + BM25 + RRF
full   = Hybrid + gte-rerank + Answerability
```

命令：

```powershell
.venv\Scripts\python.exe -m eval.run_eval --top-k 10 --save-baseline
```

输出 `eval/results/eval-*.json` 与 `eval/results/baseline.json`（只有 full 模式降级率 <50% 才覆盖基线）。

## 5. 实测结果（2026-10-23，rerank 额度可用时）

| 模式 | Recall@10 | HitRate@10 | MRR@10 | NDCG@10 | 平均延迟 |
| --- | --- | --- | --- | --- | --- |
| 随机基线 | 0.0866 | — | — | — | — |
| dense（旧） | 0.6718 | 0.7966 | 0.4819 | 0.4862 | 196 ms |
| hybrid（Dense+BM25+RRF） | 0.7041 | 0.8305 | 0.5962 | 0.5752 | 212 ms |
| full（+rerank+answerability） | **0.7439** | **0.8644** | **0.6786** | **0.6547** | 704 ms |

结论：

- Hybrid 相比纯向量：Recall +3.2%，**MRR +23.7%**，说明稀疏路把“该在第一名”的东西拉回来了；
- Rerank 相比 Hybrid：Recall +4.0%，**MRR +13.8%**，精排对排序收益明显；
- 随机基线 0.0866，说明 0.74 的 Recall 不是语料小造成的假象。

### 分桶（full 模式）

| 类型 | 条数 | Recall@10 | MRR@10 |
| --- | --- | --- | --- |
| identifier | 19 | 0.6842 | 0.5789 |
| semantic | 22 | 0.6515 | 0.5909 |
| multi_condition | 10 | 0.8500 | 0.7583 |
| multi_hop | 8 | 0.8750 | 0.8750 |
| unanswerable | 12 | —（abstention recall 1.0） | — |

## 6. 建了怎么用

### 6.1 改配置的 A/B 对比

```powershell
# 改 chunk_size 前
python -m eval.run_eval --top-k 10 --save-baseline
# 改 chunk_size 后
python -m eval.run_eval --top-k 10
# 对比 eval/results/ 下两份 JSON 的 recall/mrr
```

### 6.2 用分桶定位问题

- identifier 桶低 → 上 BM25（本项目正是这样验证的）；
- 整体 Recall 高、MRR 低 → 上 rerank；
- multi_hop 低 → 父子扩展 / 查询分解；
- unanswerable 桶有返回 → 建 Answerability。

### 6.3 接 CI 门禁

v2 §5.4 的门槛：`Recall@10 不低于 baseline - 2%`，`abstention precision ≥ 0.9`。后续可在 CI 中跑 `run_eval` 并比较 `baseline.json`。

## 7. 技术栈

| 用途 | 选型 | 理由 |
| --- | --- | --- |
| 数据集 | JSONL | 可 diff、可逐行编辑、适合放 Git |
| 指标 | 纯 stdlib（`math` / `re`） | <120 行，公式透明，无版本漂移 |
| 检索 | 复用 `VectorStoreService` | 评的就是线上同一条链路 |
| 生成候选问题 | 复用 `model.factory.chat_model` | 零新依赖 |
| 阶段 0 不引入 | RAGAS / BEIR / sentence-transformers / datasets | 会把确定性跑分变成“看模型心情” |

## 8. 反思：这一阶段做得完善吗？

**做得好的：**

- 指标公式与 IR 标准一致，且有随机基线；
- 标注存片段而非硬编码 chunk_id，切分变化可迁移；
- 三模式同批对比，收益可归因；
- 负样本 12 条，full 模式全部正确拒答（abstention recall 1.0）。

**还不完善的：**

1. **规模不足**：每个语料 50/21 条，低于 v2 建议的 50-100 条/语料；需要继续扩充 multi_hop 与多条件样本。
2. **没有双人标注与 Cohen's κ**：当前是单人标注 + 代码校验，标注一致性未量化。
3. **没有 train/holdout 划分**：所有样本都参与过观察，后续调参有过拟合风险。
4. **需求文档评测集是本地文件**：他人克隆仓库后无法复现这 21 条，只能复现论语 50 条。
5. **指标快照受索引重建影响**：Chroma HNSW 是近似检索，删除/重建后同一 query 的 Top-K 可能变化；`index_version` 目前不含“构建批次”，严格对比时应固定索引快照。
6. **尚无 CI 门禁**：现在是手动跑，下一步应把 `baseline.json` 对比脚本化。

> 结论：阶段 0 的“尺子”已经可用，但精度（样本量/一致性）和制度化（holdout/CI）还不够，属于“可指导决策的原型”，不是“可对外承诺的评测体系”。
