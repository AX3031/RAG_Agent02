# 阶段 2：Dense + BM25 + RRF + Rerank（混合检索入门）

> 面向入门：解释“为什么纯向量不够”“BM25 怎么工作”“RRF 为什么不用调参”“精排贵在哪”，并给出本项目的实测收益。
> 配套代码：`rag/sparse_index.py`、`rag/retrieval_service.py`。

---

## 1. 为什么纯向量检索不够

向量检索（Dense）把文本映射到语义空间，擅长：

- 同义改写：“学习后要复习” ↔ “学而时习之”；
- 概念解释、跨语言。

但它的盲区是**精确词面匹配**：

- 订单号 `HD-8842`、错误码 `E1042`、版本号 `v2.1`；
- 人名、地名、条款编号、古典文本中的固定搭配。

向量会把 `HD-8842` 和 `HD-8843` 映射得很近，因为它们语义上“都是订单号”。BM25（Sparse）正好相反：它只看词是否出现、出现几次、这个词有多稀有，对精确标识符极其敏感。

**混合检索 = 用两路互补的召回，再用融合算法合并排名。**

---

## 2. Dense 路

实现：`VectorStoreService.similarity_search_with_score(query, k=15, scope=...)`。

- 底层是 Chroma 的 L2 距离，越小越相似；
- 契约里的 `score.dense` 换算成 `1/(1+distance)`，方便阅读；
- `scope` 通过 Chroma 原生 `where` 过滤，在召回前生效（ACL 语义）。

---

## 3. Sparse 路：自研 BM25（不新增依赖）

### 3.1 中文分词策略

项目没有引入 jieba/tiktoken，`rag/sparse_index.py` 用正则做轻量分词：

- 连续汉字：同时生成 **unigram + bigram**；
- 英文字母/数字：按连续 token 保留 `HD-8842`、`v2.1`；
- 例：`学而时习之` → `学, 而, 时, 习, 之, 学而, 而时, 时习, 习之`。

为什么 bigram 重要：古典汉语里“学而”“为政”“孝弟”是固定搭配；只切单字会丢词序信息，只切词又需要词典。

### 3.2 BM25 公式

对 query 中的每个词项 \(t\)：

\[
score(D) = \sum_{t \in Q} IDF(t) \cdot \frac{f(t,D)\,(k_1+1)}{f(t,D) + k_1\,(1-b+b\cdot|D|/avgdl)}
\]

- \(f(t,D)\)：词项在文档中的词频；
- \(|D|\)：文档长度，`avgdl` 平均长度；
- \(k_1=1.5\)、\(b=0.75\)；
- \(IDF(t)=\ln(1+\frac{N-df(t)+0.5}{df(t)+0.5})\)。

实现要点：

- 构建时缓存 `postings: term -> [(doc_idx, tf)]`，查询只扫命中的 posting；
- `allowed_ids` 在打分前过滤，保证 scope 不越权；
- 索引按 `(index_version, 文档数)` 做进程内缓存，避免每次查询重建。

## 4. RRF：零配置的融合基线

Reciprocal Rank Fusion：

\[
RRF(d) = \sum_{r \in rankings} \frac{1}{k + rank_r(d)}
\]

- 只看排名，不看分数绝对值，因此不需要归一化两路分数；
- `k=60` 是业界稳健默认值；
- 同一文档被两路同时召回时得分叠加，天然偏向“共识结果”。

本项目 `_rrf_fuse()` 的实现：

```python
for rank, (doc, distance) in enumerate(dense_candidates, 1):
    item["rrf"] += 1 / (rrf_k + rank)
for rank, (doc, score) in enumerate(sparse_candidates, 1):
    item["rrf"] += 1 / (rrf_k + rank)
```

## 5. Rerank：单点精度收益最大的一步

RRF 之后取 Top-N 候选，送入 Cross-Encoder 精排：

- 模型：DashScope `gte-rerank-v2`（API）；
- 输入：query + 候选文本；
- 输出：`relevance_score`，按分数重排，取 Top-5；
- 失败/超时：退回 RRF 顺序，并记入 `degraded_stages`。

为什么 Cross-Encoder 更强：它把 query 和文档**拼在一起**过一遍模型，能判断“这段文字是否真的回答了这个问题”；而双塔向量只比较两个独立向量的距离。

### 5.1 熔断与额度

实测中 DashScope 免费额度会耗尽（HTTP 403）。实现：

- 403/401 不重试，直接失败；
- 连续失败 3 次后熔断 120 秒，后续请求跳过 rerank（`rerank_circuit_open`）；
- 结果仍可用（RRF 排序），只是 `status=degraded`。

这让“上游不可用”不会拖垮整个 RAG 子 Agent。

## 6. 实测收益（同一批 71 条 Golden Set）

| 模式 | Recall@10 | HitRate@10 | MRR@10 | NDCG@10 | 平均延迟 |
| --- | --- | --- | --- | --- | --- |
| dense | 0.6718 | 0.7966 | 0.4819 | 0.4862 | 196 ms |
| hybrid | 0.7041 | 0.8305 | 0.5962 | 0.5752 | 212 ms |
| full | **0.7439** | **0.8644** | **0.6786** | **0.6547** | 704 ms |

读法：

- **Hybrid 的 MRR 提升 23.7%**：说明 BM25 把“本来排在第 5、第 8 的正确块”拉到了前面；
- **Rerank 的 MRR 再提升 13.8%**：说明精排对“第一条是不是对的”很有效；
- 延迟从 196ms → 704ms，主要花在 rerank（~200ms）和 Answerability LLM（~300ms）。

### 6.1 分桶看短板

- `identifier` 桶：BM25 收益最明显；
- `semantic` 桶：Dense 本来就好，混合后略升；
- `multi_hop` 桶：Recall 高但 MRR 不一定高，需要父子扩展/查询分解；
- `unanswerable` 桶：与排序无关，靠 Answerability 解决（见阶段 3）。

## 7. 一个真实失败案例

`ly-005`「孔子说自己十五岁到七十岁分别达到什么境界？」：

- 正确原文是「吾十有五而志于学，三十而立……七十而从心所欲」；
- 查询用现代汉语“十五岁”，原文用“十有五”；
- BM25 的 bigram `十五` 与 `十有`/`有五` 不匹配；
- Dense 也被“境界”“达到”等现代词带偏，Top-15 没进正确块。

结果：检索未命中 → Answerability 正确判为“证据不足”。这不是 Answerability 的错，而是**查询改写/领域 Embedding** 的缺口。

改进方向：

1. 查询改写：把“十五岁”改写成“十有五”；
2. 章节标题/实体扩展；
3. 换更适合古典汉语的 Embedding（生产期 BGE-M3）；
4. 对高频实体建同义词表。

---

## 8. 反思：这一阶段做得完善吗？

**做得好的：**

- 不做“全家桶”：Chroma + 自研 BM25 + DashScope rerank，符合 v2 的验证期选型；
- 三种模式同批对比，收益可归因；
- 熔断/降级完整，上游 403 不会拖垮链路；
- 日志只记录 query_hash 与 evidence_id，不落全文。

**还不完善的：**

1. **BM25 是内存态**：不支持增量删除、多进程不一致；生产应换 Qdrant sparse / BGE-M3 sparse。
2. **没有查询改写**：古典汉语/指代式查询仍会漏；v2 把 rewrite 列为可选，但本项目已暴露这个短板。
3. **没有父块参与精排**：目前只用子块文本送 rerank，父块只做上下文扩展；可尝试“子块精排 + 父块重排”。
4. **rerank 额度不可控**：免费额度耗尽后 full 模式退化为 hybrid；需要预算/告警，或生产期自托管 bge-reranker-v2-m3。
5. **RRF 参数未做敏感性分析**：k=60 是默认值，没有用 Golden Set 扫过 10/30/60/100。
6. **没有 query 类型路由**：所有查询都走同一条链路；可以按 identifier/semantic 分流（identifier 提高 sparse 权重）。

> 结论：混合检索的“主干”已经跑通并有可验证收益，但查询改写、参数敏感性、生产级 sparse 存储仍是下一轮工作。
