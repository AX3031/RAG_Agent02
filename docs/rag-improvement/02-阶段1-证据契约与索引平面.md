# 阶段 1：证据契约与索引平面（从“问答 POC”到“可编排子 Agent”）

> 面向入门：解释为什么要改输出协议、为什么要给每个块发“身份证”、文档更新/删除如何传播，以及这些改动在代码里具体落在哪。
> 配套代码：`rag/contract.py`、`rag/chunking.py`、`rag/index_store.py`、`rag/vector_store.py`。

---

## 1. 旧实现的两个根本问题

### 1.1 输出是一段不可追溯的自然语言

旧 `rag_summarize` 返回：

```text
“学而时习之”出自《论语·学而》……
```

问题：

- 主 Agent 无法知道这句话来自哪个文档、哪个版本、哪一页；
- 无法校验引用是否来自本次检索（模型可以编一个“参考资料 9”）；
- 无法判断“证据是否足够”，只能由生成模型自由发挥；
- 无法做检索侧评估，因为输出里没有检索结果。

### 1.2 索引只增不删（TD-07）

旧逻辑只记录 `md5.text`：

```text
文件内容变化 → 新 MD5 → 新增一批 chunk → 旧 chunk 永远保留
```

后果：检索到过期内容；`md5.text` 无法反查文件路径；删除文档无从下手。

## 2. 证据契约：子 Agent 的“接口协议”

`rag/contract.py` 定义了完整的响应结构。核心字段：

```json
{
  "contract_version": "1.0",
  "request_id": "req_xxx",
  "trace_id": "trace_xxx",
  "status": "ok | no_evidence | degraded | denied | error",
  "answerable": true,
  "error": {"code": "INVALID_QUERY", "message": "..."},
  "evidence": [{
    "evidence_id": "ev_001",
    "doc_id": "论语-69b3e2",
    "version": "419b729c...",
    "chunk_id": "论语-69b3e2#419b729c#c0000",
    "parent_id": "论语-69b3e2#419b729c#p0000",
    "title_path": ["卷一　学而第一"],
    "page": 1,
    "char_start": 0,
    "char_end": 209,
    "text": "...",
    "context": "...",
    "score": {"dense": 0.55, "sparse": 28.8, "rrf": 0.032, "rerank": 0.53},
    "scope_tags": ["public"]
  }],
  "degraded_stages": ["rerank_timeout"],
  "latency_ms": {"dense": 45, "sparse": 30, "fuse": 2, "rerank": 180, "expand": 30, "total": 307},
  "index_version": "idx-fca9ff4e07"
}
```

### 2.1 状态机的语义（严格按 v2 §1.3）

| status | 含义 | answerable | 主 Agent 动作 |
| --- | --- | --- | --- |
| `ok` | 检索正常且证据充分 | true | 直接使用证据 |
| `no_evidence` | 检索正常但证据不足 | false | 改写 query 或放弃，**不得硬生成** |
| `degraded` | 部分链路降级（rerank 超时/额度不足） | 视情况 | 可接受；必要时降级重试 |
| `denied` | 权限不足 | false | 不重试，提示无权限 |
| `error` | 系统性错误 | false | 按 `error.code` 决定有限重试 |

`error.code`：`TIMEOUT / INDEX_STALE / UPSTREAM_5XX / RATE_LIMIT / INVALID_QUERY / DENIED / NO_EVIDENCE`。

### 2.2 三条硬约束

1. 所有响应必须携带 `contract_version / request_id / trace_id / index_version`；
2. `status=error` 时 `answerable` 必须为 false；
3. `evidence_id` 必须来自本次检索结果，生成答案的引用要能被校验（`validate_evidence_ids`）。

### 2.3 为什么 evidence 里同时有 `text` 和 `context`

- `text` 是**子块**正文，精排命中的是它；
- `context` 是按 `parent_id` 取回的**父块**正文，用于给生成模型更完整的上下文，避免“小块断章取义”。

## 3. 索引平面：给每个块发“身份证”

### 3.1 确定性 ID

`rag/chunking.py`：

```text
doc_id    = 文件名 + 路径哈希（如 论语-69b3e2）
version   = 文件内容 md5
chunk_id  = {doc_id}#{version[:8]}#c{seq:04d}
parent_id = {doc_id}#{version[:8]}#p{seq:04d}
index_version = idx-{sha1(分块算法+参数+Embedding 模型)}
```

好处：

- 同一文件、同一参数 → ID 完全一致，Golden Set 可复用；
- 版本变化 → `version` 变化，新旧块 ID 不同，可精确删除旧版本；
- `index_version` 变化 → 说明分块/模型变了，评测结果不可直接比较。

### 3.2 父子分块与元数据

每个子块携带（v2 §4.1）：

```text
doc_id / version / chunk_id / parent_id / seq
source / page / char_start / char_end / title_path
content_hash / scope_tags / embedding_model / index_version / is_active
```

分块策略：

- 识别 Markdown 标题、`卷X　篇名`、`第X章`；
- 《论语》的对话行（子曰/有子曰/某某问）作为块边界；
- 子块 240 字 / overlap 40，父块 900 字；
- 标题文本包含在父块里，避免“只有标题的碎片块”。

结果：

```text
论语.pdf          52 父块 / 142 子块
rag_requirements  42 父块 /  95 子块
总计              96 父块 / 239 子块
```

### 3.3 索引清单（替代 `md5.text`）

`rag/index_store.py` 的 `IndexManifest`：

```json
{
  "index_version": "idx-fca9ff4e07",
  "updated_at": "2026-10-23T22:48:34+08:00",
  "files": {
    "data/论语.pdf": {
      "doc_id": "论语-69b3e2",
      "version": "419b729c259e0b1975c41273dee56c82",
      "chunk_ids": ["..."],
      "parent_ids": ["..."],
      "chunk_count": 142,
      "parent_count": 52
    }
  }
}
```

写入使用**临时文件 + `os.replace`**，避免半写坏文件；清单损坏时备份为 `.corrupt` 并重建。

### 3.4 更新与删除传播

`VectorStoreService.load_document()` 的语义：

1. 新文件：切分 → 写父块 → 写子块 → 登记清单；
2. 已存在且 MD5 相同：跳过；
3. 已存在但 MD5 变化：**先写新版本，成功后再删除旧版本块**；
4. 文件从磁盘消失：`prune=True` 时级联删除块、父块、清单记录；
5. `--rebuild`：清空当前集合与父块，重新入库；
6. `--delete-doc <doc_id>`：按文档级联删除。

实测：

```text
before       chunks=239 files=4 parents=96
delete_doc(测试文本-8e4760) → chunks=238 files=3 parents=95
load_document() → 只重索引 data/测试文本.txt，其余 3 个文件 skip
after        chunks=239 files=4 parents=96
```

这证明 TD-07「只增不删」已被修复。

## 5. 反思：这一阶段做得完善吗？

**做得好的：**

- 契约字段与 v2 §1 对齐，状态机、error.code、公共字段齐全；
- 确定性 chunk_id 与父子分块落地，Golden Set 可迁移；
- 更新/删除传播有实测，不再只增不删；
- 写入原子化，清单损坏有备份。

**还不完善的：**

1. **没有软删除/墓碑/GC**：删除是硬删除，v2 §4.2 建议 `is_active/deleted_at` + tombstone + 定期 GC；当前只有 `is_active=True` 字段，没有真正使用。
2. **没有 ingestion 队列 / DLQ**：单文件失败只记录日志，不能查询、不能重放。
3. **没有 embedding 升级迁移**：没有双写、影子索引、别名切换；只有 `index_version` 校验兜底。
4. **ACL 只是接口形态**：`scope` 支持按元数据精确过滤，但没有真实鉴权上下文，`scope_tags` 只有 `public`。
5. **分块按字符而非 tokenizer**：`chunk_size=240` 是字符数；v2 §4.5 要求按模型 tokenizer 计 token，当前没有 tiktoken 依赖，属于已知偏差。
6. **父块存储是单 JSON**：文档量大时会膨胀，生产应换 PostgreSQL（项目已有 PG 依赖）。
7. **没有文档解析报告**：PDF 扫描件/表格解析失败没有 `conversion_report`。

> 结论：契约与索引的“骨架”已经可用，但运维语义（软删除、队列、迁移、ACL、tokenizer）仍是生产化缺口。
